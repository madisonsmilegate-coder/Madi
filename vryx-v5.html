FAQ

Straight answers to
straight questions.

VRYX groups alerts using time-window clustering and service dependency graphs. You define your topology once via config file or API; the engine uses that graph to determine blast radius and suppress redundant pages. No "AI" inference — deterministic, auditable logic you can inspect.

Yes. Enterprise customers can deploy VRYX inside their own VPC using the Docker image and Helm chart. State is stored in Postgres + Redis — nothing proprietary. Cloud and self-hosted versions share the same codebase.

Cloud: 30 days on Startup, 90 days on Scale, custom on Enterprise. All data is encrypted at rest (AES-256) and in transit (TLS 1.3). You can export your full dataset at any time via the REST API. Self-hosted customers manage retention themselves.

Runbooks are YAML files with typed steps: HTTP calls, shell commands, Slack messages, PagerDuty escalations. They live in your Git repo and VRYX syncs them via webhook. Every execution is logged with full step output — searchable by incident ID.

The ingest pipeline is multi-region active-active. The dashboard has a degraded mode that shows cached state. On-call notifications have a direct-to-carrier SMS fallback. Our SLA is 99.9% uptime — we publish our own ops data at status.vryx.io.
